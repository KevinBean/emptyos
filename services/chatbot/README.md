# EmptyOS Chatbot Service

Standalone FastAPI service for Publish content assistants and Studio-managed website shopping assistants.

**Lane 1 service — no vault.** Independent of the EmptyOS daemon: sites keep working when this is down; this keeps working when the daemon is down. Deployed at `chat.<yourdomain>` behind Caddy. See `docs/DEPLOYMENT.md` § "Lane 1 — Service" for the conventions this directory follows.

## What it does

1. Accepts `POST /chat` from a whitelisted site origin.
2. Fetches that site's `corpus.json` (built by `apps/publish/builder.py`).
3. Tries an FAQ pre-bake (free, instant).
4. Falls through to OpenAI — concise reply, capped tokens, capped daily $.
5. Records every call in a SQLite ledger.

When `commerce_enabled = true`, deterministic catalogue search runs before the
model and returns typed product/action blocks. Price, availability, order, and
return values are never generated by the model. Cart mutation requires a widget
button click; sensitive action form values go directly to the configured connector.

## Anti-abuse

| Layer | Mechanism |
|---|---|
| Origin lock | Reject if `Origin` header not in site's allowlist (401) |
| Token caps | Reject input > `max_input_chars`; cap output at `max_output_tokens` |
| Per-IP rate limit | SQLite ledger, 20/hour + 60/day per IP (429) |
| Per-site $ cap | Reject when site hits `daily_cap_usd` (429, retry after midnight UTC) |
| Global $ cap | Reject when sum across sites > `global_cap_usd` (last-line) |
| Topic gate | System prompt instructs model to refuse off-topic |
| Logging | Every call → SQLite `requests` table |

## Architecture — the external-site instance of the conversation stack

This service is the same shape as EmptyOS's in-daemon assistants (the page
companion rail and Aura, `docs/CONVERSATION-STACK.md`), with one substitution:
those reach their data and verbs **directly**; here there is no vault, no kernel,
and no `call_app`, so a **digest layer** stands in the middle.

```
external site  →  emptyos digest  →  chat
```

| Layer | Page-assistant / Aura (in-daemon) | This service (external site) |
|---|---|---|
| **Data** | direct — `vault_query`, app state | **digest** — `crawler.py`/`corpus.py` (site → corpus), `ensure_catalog_feed` (feed → catalogue) |
| **Verb declaration** | manifest `[[provides.verbs]]` → verb registry | `sites.toml` per-site `allowed_actions` + `action_endpoint` |
| **Routing** | `[INTENT:app.verb]` / `select()` | `commerce_reply()` — deterministic keyword selector, runs **before** the model |
| **Action gate** | review gate + eligibility floor | `secure_action_form` blocks — values go to the connector, never the model; a human clicks Continue |
| **Dispatch** | `call_app(app, method)` | `_post_connector` → the site's endpoint (or `demo://`) |
| **Surface** | companion rail / Aura | `chatbot-widget.js` |

### The digest layer owns what the site can't be asked

The load-bearing rule: **whatever state the external site cannot be queried for,
the digest layer owns — or the verb has nothing behind it.**

The session cart is the worked example. `cart.add` existed as a verb while
nothing stored a cart, so "check my cart" fell to the model, which correctly
refused (it has no cart to read) — a verb declared with no state behind it. The
fix was not prompt-side: every successful `cart.add` now mirrors into
`ledger.cart_items` keyed `(site_id, session_id)`, and the cart question is a
deterministic intent served from that mirror. The mirror is scoped honestly —
it is *what this chat added*, never a claim about the store's authoritative
cart, which stays the source of truth at checkout.

Applies the same way to any future verb: if the answer isn't in the corpus, the
catalogue, or the ledger, the model must not be the one to invent it.

### Boundary — patterns port, code does not

The service stays Lane 1: it never imports the EmptyOS SDK, kernel, or verb
registry. What crosses is *discipline*, not modules — deterministic selector
ahead of the model, propose→confirm before any state change, verb declaration as
config, and provenance on every reply (`source`, rendered as the widget's badge).
Keep it that way: a site's assistant must keep working when the daemon is down.

## Quick start (local)

For the normal EmptyOS developer installation, install the root optional group
once with `pip install -e ".[chatbot]"`. `restart.bat` then starts the managed
External Lab Host on `http://127.0.0.1:9100`, mounts this service at `/chatbot`,
and stores its generated config, token, catalogue, and logs under
`data/external-lab/`. No service-local `.env` or `sites.toml` is required.

To run this service independently instead:

```bash
cd services/chatbot
pip install -e .

cp sites.toml.example sites.toml  # edit per-site config
export OPENAI_API_KEY=sk-...
export CHATBOT_ADMIN_TOKEN=$(python -c "import secrets; print(secrets.token_urlsafe(32))")

uvicorn main:app --host 127.0.0.1 --port 8000
```

Test:

```bash
# Health
curl -s http://127.0.0.1:8000/health

# Chat (must include Origin matching sites.toml allowed_origins)
curl -s -X POST http://127.0.0.1:8000/chat \
  -H "Origin: https://eos.binbian.net" \
  -H "Content-Type: application/json" \
  -d '{"site_id":"eos","messages":[{"role":"user","content":"What is EmptyOS?"}],"session_id":"test"}'
```

Expected negative responses:
- Missing/wrong `Origin` header → 401
- Message > 4000 chars → 400
- 21 requests in <1h from same IP → 429 on 21st
- Cumulative $ > daily cap → 429 with `Retry-After` header

## Quick start (Docker, via standard deploy script)

The Lane-1 standard says: every service deploys with `scripts/deploy-service.sh <name>`. For the chatbot:

```bash
# One-time setup on a host
cd services/chatbot
cp .env.example .env && nano .env          # set OPENAI_API_KEY + CHATBOT_ADMIN_TOKEN
cp sites.toml.example sites.toml && nano sites.toml
sudo cp caddy.snippet /etc/caddy/sites/chatbot.caddy
sudo systemctl reload caddy

# Deploy (idempotent — safe to re-run)
bash ../../scripts/deploy-service.sh chatbot
```

The deploy script reads `service.toml`, runs `docker compose --env-file .env up -d --build`, polls `/health` until 200, and reports status. Service binds to `127.0.0.1:9100` on the host.

For a one-off ad-hoc run without the script:
```bash
docker compose --env-file .env up -d --build
docker compose logs -f
```

## Refresh corpus cache

When you rebuild a site and want the new content live immediately (otherwise wait for `corpus_ttl_seconds`):

```bash
curl -X POST https://chat.yourdomain.com/admin/refresh/eos \
  -H "X-Admin-Token: <CHATBOT_ADMIN_TOKEN>"
```

## Files

| File | Role |
|---|---|
| `service.toml` | Lane-1 manifest — name, vhost, port, healthcheck (read by `deploy-service.sh`) |
| `caddy.snippet` | Drop-in Caddy vhost block; copy into `/etc/caddy/sites/chatbot.caddy` |
| `.env.example` | Documented env vars; copy to `.env` and fill in |
| `sites.toml.example` | Per-site config template; copy to `sites.toml` and fill in |
| `docker-compose.yml` | Compose stack (no `<name>` infix — Lane-1 standard) |
| `Dockerfile` | Image build |
| `main.py` | FastAPI app + routes + middleware-shaped gates |
| `config.py` | Loads `sites.toml` |
| `corpus.py` | Per-site corpus fetch, in-memory TTL cache, FAQ matcher |
| `crawler.py` | Bounded explicit-URL/sitemap crawler with untrusted-content fencing |
| `commerce.py` | Versioned catalogue normalization, feed refresh, deterministic product discovery |
| `site_secrets.py` | Deployment-local connector credentials |
| `ledger.py` | SQLite — rate limits + $ tracking + Q&A log |
| `providers/openai_provider.py` | OpenAI chat-completions impl |
| `providers/base.py` | Provider ABC for swapping backends later |

## Adding a Studio-managed commerce site

Use Chatbot Studio in EmptyOS, or call authenticated `POST /admin/sites`.
Supply `knowledge_sources` (explicit pages or a sitemap), a `catalog_url` JSON
feed or CSV import, browser origins, and an explicit `allowed_actions` list.
Create the site disabled, test it through `/admin/sites/{id}/test`, then enable
it. Publish-owned sites default to `managed_by = "publish"` and are read-only
in Studio.

```html
<script src="https://chat.example.com/widget/chatbot-widget.js"
  data-chatbot-site="shop" data-chatbot-endpoint="https://chat.example.com" defer></script>
```

## Adding a Publish site

1. Build the site with EmptyOS publish app — `corpus.json` lands at the site root.
2. Add a `[sites.<id>]` block to `sites.toml`.
3. Restart the service (or `docker compose restart chatbot`).
4. Hit `/admin/refresh/<id>` to skip the cache wait.

## Controlled printer pilot

Set `CHATBOT_DEMO_ENABLED=1`, set `CHATBOT_PUBLIC_ORIGIN` to the public service
origin, then use **Create printer pilot** in Chatbot Studio. This creates a
Studio-owned `printer-pilot` site, 120 synthetic office products, a demo
connector, and `/demo-store/`. The flag is off by default; no external retailer
data or branding is used.

## Adding a new LLM provider

1. New file `providers/<name>_provider.py` implementing `Provider` from `providers/base.py`.
2. Register in `providers/__init__.py:get_provider`.
3. Add pricing dict if charging per-token.
4. Set `defaults.provider = "<name>"` in `sites.toml` (or override per-site — TODO when 2nd provider lands).
