# Authorship Boundary — every vault file has one owner

A vault note's *author* is either the user, the system, or both. Today EmptyOS
distinguishes them only at render time — `EOS_UI.provenance()` shows a 🔒/☁/👤
chip when a UI consumes AI output. The chip is fine for inference traces, but
when AI-generated content lands in the vault (reactor breadcrumbs, distilled
KB notes, conversation digests, generated PDFs), the file itself looks like
the user wrote it. Six months later: "did I write this, or did Claude?"

This rule encodes authorship at the **write boundary** instead. The render
chip stays; folder + frontmatter convention makes authorship structural.

CLAUDE.md rule 11 (reactive vault population) is the precedent: reactor writes
journal breadcrumbs into the daily note. This rule generalises that — *any*
app writing AI-authored content into the vault declares the authorship, and
contributors can tell apart at a glance which lines were AI-written without
running the app that produced them.

## The three states

| Author | Meaning | Examples |
|---|---|---|
| `user` | Human-authored. AI never modifies, only reads. | Daily journal entry body, hand-written project notes, captures, reference notes |
| `ai` | System-authored. Generated by an LLM call, reactor handler, or analyser. | Conversation digests, project health summaries, distilled KB notes from chat transcripts |
| `both` | Co-authored. Human seeded the note, AI edits/extends it (or vice versa). | Job application notes where the user writes prose + an app appends a timeline event; project main notes where reactor adds breadcrumbs to a user-curated body |

The rule that does the work: **every file declares one of these three.** Not
"sometimes," not "mostly." One. If both have touched the file, it's `both`
— the label is exact, not approximate.

## Convention

### Frontmatter field

```yaml
---
author: ai          # or: user | both
---
```

Defaults when absent:

- Files under `30_Resources/EmptyOS/<app>/outputs/` → implicit `author: ai`
- Files under `00_Inbox/`, `10_Projects/`, `50_Journal/` → implicit `author: user`
- Daily journal notes that reactor appends to → explicit `author: both`
  (the reactor handler must set this when it inserts a breadcrumb into a
  pre-existing user note)

Defaults exist so 4,000 legacy notes don't need backfilling. New write paths
should set the field explicitly.

### Folder convention for AI-output subfolders

When an app writes AI-authored content under its vault home, place it in an
`outputs/` subfolder:

```
30_Resources/EmptyOS/<app>/
├── *.md              ← user-shaped notes (settings, prompts, configs)
└── outputs/          ← AI-authored artifacts
    └── *.md
```

A glance at the folder name tells the reader. Renames are not retroactive —
existing apps keep their layout; new write paths follow the convention.

### Both-author notes — append discipline

When AI appends to a user note (the journal-breadcrumb shape):

- AI writes only inside a clearly-marked section (`## Reactor` or `## Timeline`
  with date-prefixed bullets), never anywhere else.
- The note's `author:` flips to `both` the first time AI appends.
- AI never edits user-written text in a `both` note. Append, don't modify.
  The journal `_daily_lock()` pattern (CLAUDE.md § Development Gotchas)
  enforces serialisation; append discipline enforces ownership.

## What this changes

| Today | After |
|---|---|
| Provenance chip at render time only | Chip + frontmatter + folder name |
| Reactor breadcrumb indistinguishable from a user-written bullet six months later | `## Reactor` section marker + `author: both` makes the boundary explicit |
| AI-generated KB notes filed next to user-curated KB notes with no distinction | `outputs/` subfolder under the writing app's vault home |
| "Did I write this?" needs `git log` | Frontmatter answers in one line |

## What this does NOT change

- The `data/` vs vault split (CLAUDE.md § Storage & Vault). Telemetry stays
  in `data/`, vault stays for content humans care about. `author:` lives only
  on vault notes.
- Existing apps' folder layouts. The `outputs/` convention applies to new
  write paths; old paths grandfather in.
- Render-time provenance. `EOS_UI.provenance()` keeps doing what it does;
  this rule is the durable file-system version of the same signal.
- Single-author files don't need an `author:` field if the folder default
  is correct. Only declare when it disagrees with the default — and always
  declare for `both`.

## SDK extraction trigger

Today two write paths touch user-shaped folders with AI-authored content:
the reactor (journal breadcrumbs) and conversation-digest skills (KB notes).
Both will need to set `author:` explicitly when they touch a note that didn't
exist or that doesn't already have the field.

Per CLAUDE.md rule 9, the SDK helper waits for the **second concrete consumer
asking for the same plumbing**. The natural shape when it lands:

```python
    # = no-op for the author flip if currently "ai" or "both"
```

Until that second consumer, each writer handles its own author-field updates.
Reactor (the first consumer) is the reference implementation.

## When NOT to use this

- Generators that write to `30_Resources/EmptyOS/<app>/outputs/` already
  declare authorship via folder. Adding the frontmatter field is redundant.
- Pure user-authored apps (capture, manual journal entries, task creation
  from UI) — folder defaults cover them. Don't add `author: user` everywhere.
- Files outside the vault (`data/`, `dist/`, `.cache/`) — they're machine
  state, not authored content. The rule doesn't apply.
- Files whose `author:` is genuinely ambiguous because the system can't tell
  (legacy notes from before this rule). Don't backfill — let the default
  apply and update on next touch.

## Anti-patterns

- **Declaring `author:` everywhere defensively.** The defaults exist so most
  files don't need it. Declare when it disagrees with the default, or always
  for `both`.
- **Flipping `author: both → user`** because "the user touched it last."
  Once `both`, stays `both` — the AI's prior contribution is still in the
  history.
- **Adding `author:` as a third axis next to `tags:` + `type:`** for queries
  ("find all AI-authored notes"). That's a render-time question and
  `EOS_UI.provenance()` already answers it for active surfaces. The rule's
  point is *write-side* clarity, not a new query dimension.
- **Renaming existing folders to fit the `outputs/` convention.** Gentle
  migration: new write paths follow the convention, existing layouts
  grandfather in. A weekend reorganisation is the wrong cost.
